# 챕터 4. 최신 AI 환경의 프롬프트 엔지니어링 — 핵심 요약 노트

> 원문: `markdown/4_최신 AI 환경의 프롬프트 엔지니어링_r3.md` (39페이지)

## 챕터 개요

이 챕터는 프롬프트 엔지니어링의 정의부터 출발하여, 최신 AI 모델(Reasoning model) 시대에 맞는 프롬프트 가이드라인을 다룬다. 핵심은 두 가지 흐름이다: ① 과거식 "지시 방법 나열"형 프롬프트에서 벗어나 **불필요한 제약을 걷어내는 '프롬프트 다이어트'**, ② Anthropic 엔지니어(Thariq Shihipar)의 강연에서 비롯된 **'미지의 영역(unknowns) 축소' 접근** — 산출물을 만들기 전에 Blindspot Pass → Brainstorms and Prototypes → Interviews의 3단계 Best Practice를 수행하는 것. 실습으로는 HBF 기술 성능 예측 발표 자료 제작을 통해 네 가지 기법(Blindspot Pass, Prototypes, Interviews, Quizzes)을 직접 적용해본다.

## 핵심 요점

### 1. 프롬프트 엔지니어링의 정의 — '공학'의 의미
- 과학에서의 공학(Engineering)은 수학·과학적 원리로 현실 문제를 기술적으로 해결하는 학문이다.
- AI에서의 공학은 이와 달리 **"원하는 LLM 출력 결과를 얻기 위한 노하우들의 모음"** 이다.
- 즉 프롬프트 엔지니어링은 거창한 학문이 아니라, AI에게 일을 잘 시키기 위한 실용 노하우의 집합이다.

### 2. 2020년식 프롬프트 엔지니어링 — "지시 방법" 중심
- 아르바이트생에게 일을 시킬 때의 노하우를 AI에 그대로 적용한 발상: ① 역할부여(페르소나) — "넌 최고의 설명 전문가" / "넌 세계 최고로 손이 빠른 알바생이야", ② 목표지정 — "테이블을 3초 안에 정리해야 해", ③ 조건지정 — "어려운 용어는 빼줘" / "손님이 없는 경우에만", ④ 예시 제시.
- 당시 유행했던 기법들:
  - **Few-shot**: 예를 여러 개 들기
  - **CoT (Chain of Thought)**: "단계별로 생각해줘"라는 키워드와 함께 질문
  - **Role 프롬프팅**: 역할 부여, 페르소나라고 불렸음
  - **Reflection**: 답이 맞는지 한번 더 검토하라고 지시
- 그러나 **Gemini 3.0 같은 Reasoning model 이후에는 위 노하우 적용 여부에 따른 결과 차이가 크게 달라지지 않는다** — 모델 스스로 이해력을 높였기 때문.

### 3. 2026년식 프롬프트 엔지니어링 — 인간과 함께 목적 탐색
- 과거 기법(예시 추가, 단계별 사고 지침 추가)은 모델의 이해력을 높이기 위한 노력이었다면, 최신 기법은 **인간과 함께 구체적인 목적을 탐색**하는 방향이다.
- 두 가지 원칙:
  1. **불필요한 사족을 걷어내기** (프롬프트 다이어트)
  2. **디테일에 대해 인간과 탐색 시작**

### 4. 프롬프트 다이어트 — 걷어내기의 3단계
예시 프롬프트 "유럽 반도체 시장 진출 전략 보고서를 써줘"(서론/본론/결론 3단 구조, 서론 시장규모 3문장, 경쟁사 A·B·C 단점 각 2개씩, 결론 5줄 이내, 무역협회 자료 참고, 전문적 문어체, 접속사 금지 등의 과잉 제약)를 단계적으로 줄여나가는 실습:
1. **수정 1 — 덜 중요한 제약 제거**: 한정된 에너지(모델의 처리 자원)를 중요한 전략에 집중시킨다. 덜 중요한 내용은 중요한 내용이 만들어진 뒤에 요청해도 늦지 않다. (구조·문체 조건 삭제, "시장규모와 경쟁사 분석도 필요해"만 추가)
2. **수정 2 — 후속 턴으로 미루기**: 덜 중요한 내용(결론 요약, 자료 출처 지정)은 보고서 완성 후 다음 대화 턴에서 요청할 수 있으므로 일단 걷어낸다.
3. **수정 3 — 사고 제약 제거**: "무역협회 자료를 참고해" 같은 지시는 인간이 생각지 못한 더 많은 정보를 AI가 찾는 것을 막는 **사고의 제약**이 되므로 제거한다.
4. **수정 4 — 목적과 필요 내용 추가**: 구체적인 방법(How)보다 **무엇(What)에 집중**하고, AI가 자율성을 갖고 목적을 달성하도록 한다. 예: "이 보고서는 경영진에게 우리 브랜드의 성공 가능성을 타진하기 위한 목적이야. 꼭 넣어야 할 정보: ① 시장규모와 경쟁사 분석 ② 성공 확률이 높은 타겟과 유통 채널 제안 ③ 경영진이 핵심 리스크와 기회 요인을 한눈에 파악 가능."

### 5. 좋은 프롬프팅이 어려운 이유 — 미지의 영역
- 지시할 목적이 명확해도, **구체적인 내용에 대해 인간의 생각이 정리되지 않았거나 충분한 지식이 없으면** 만족스러운 결과를 얻기 어렵다.
- 프롬프팅의 목표는 AI와의 대화를 통해 사람이 생각하지 못한 **"미지의 영역(unknowns)"을 줄이는 것** — 사람 머릿속에만 있거나 아직 구체적으로 결정하지 않은 것을 AI와 함께 정한다.
- 출처: Anthropic Claude Code 팀 Thariq Shihipar(타릭 시히파르)의 2026년 고성능 모델 'Fable' 사용 노하우 강연 (YouTube + claude.com/blog "A field guide to Claude Fable: finding your unknowns").

### 6. 산출물 제작 전 3가지 Best Practice

**① Blindspot Pass (사각지대 통과)**
- 잘 모르는 건 지시하기도 어렵다 — 먼저 AI와 대화하며 배운다.
- 3단계 실습 (HBF 기술 발표 자료 예시):
  1. 본인의 사각지대 파악: "HBM과 SSD의 느린 속도를 보완하기 위한 HBF 기술을 설명하고… 내가 만들어달라고 직접적으로 말할 때까지 만들지 마. 중학생도 이해할 수 있게 설명을 짧고 쉽게 해줘" — *만들지 말고 먼저 설명*하라고 지시하는 것이 포인트.
  2. 이해 검증: 이해한 내용을 되짚어 "…이 것이지? 내가 이해한 것이 맞아?" / "확실해?"로 확인.
  3. 더 나은 이해: "HBM, SSD, HBF를 쉽게 이해할 수 있는 인터랙티브한 Web App을 만들어줘" (인터랙티브 App = 클릭에 콘텐츠가 즉각 반응하는 App).

**② Brainstorms and Prototypes (브레인스토밍과 시안)**
- AI에게 지시하기 전 먼저 브레인스토밍: "지금부터 브레인스토밍 해볼게. 어떤 흐름으로 발표 자료를 제작하면 좋을까?" (개념 설명·성능·결론 등 필요 요소를 가벼운 대화로 정리)
- Prototypes 받기: "HBF로 인해 성능이 좋아질 수 있음을 효과적으로 설명할 수 있는 후보 3개를 보여주는 인터랙티브한 Web App을 만들어줘. 후보 1, 2, 3 중 마음에 드는 것을 내가 채팅으로 알려줄게" — **내가 선택할 수 있게 선택지를 받는다**.
- 후보 중 하나를 골라 답변("후보 1이 마음에 드네")하면 방향이 확정된다.

**③ Interviews (인터뷰)**
- 브레인스토밍을 충분히 해도 여전히 미지의 세계가 남아있을 수 있다.
- "발표 자료를 제작하기 전, 모호한 부분은 한번에 하나씩 질문해줘" — **AI가 나에게 궁금한 것을 물어보도록** 하여 미지의 영역을 알아낸다. 질문에는 적절히 대답한다.

### 7. 보조 기법 — References와 Quizzes
- **References**: 잘 만들어진 문서(샘플)를 AI에게 제공 — 원하는 바를 자세히 설명하기 어려울 때 참고자료를 주는 것도 좋은 방법.
- **Quizzes**: "발표 자료 내용을 내가 완벽히 이해했는지 확인하는 용도로 O, X 퀴즈 4개를 내줘" — AI가 만든 요약을 단순히 읽는 데서 끝내지 않고 **실제 이해도 확인**에 활용.
- 마무리로 "지금까지 입력한 프롬프트를 정리한 HTML 문서를 만들어줘" — 기법별로 내가 어떤 프롬프팅을 했는지 정리·복습.

## 실습/적용 포인트

- **프롬프트 다이어트 실습**: 주어진 프롬프트(여행지 추천 보고서 등)를 직접 수정해본다. 주안점 ① 구체적인 제약사항 줄이기 ② "어떻게 생각해야 하는지" 제거하기 ③ 필요한 배경(목적·What) 추가하기 ④ 구체적으로 원하는 것만 추가하기.
- **HBF 발표 자료 실습**: 모르는 기술(HBM/SSD/HBF) 주제로 Blindspot Pass(설명 요청 → 이해 검증 → 인터랙티브 Web App) → Brainstorming → Prototypes(후보 3개 → 선택) → Interviews(한번에 하나씩 질문) → "지금까지 대화를 기반으로 발표 자료를 제작해줘. Web 기반, 인터랙티브하게" 순서로 진행.
- **[미션 5] 도전 과제**: 스페이스X 협업으로 우주에서 버틸 수 있는 메모리(DDR7의 우주 환경 신뢰성) 주제. ① 네 가지 기법(Blindspot Pass / Prototypes / Interviews / Quizzes) 프롬프트를 적용해 실습 ② 사용한 프롬프트를 정리한 HTML 파일 제출 (AI Studio > 과제) ③ 완성된 Web App 발표 자료를 단체 채팅방에 공유.
- 일상 적용 팁: 산출물을 바로 요청하기 전에 "만들지 말고 먼저 설명해줘"부터 시작하고, 방향이 정해지지 않았으면 선택지(prototype)를 여러 개 받아 고르는 습관이 최신 모델에서 더 좋은 결과를 낸다.

## 궁금한 점

- Reasoning 모델에서 Few-shot/CoT가 "효과 없다"고 단정하는 근거 — 유형별(창작 vs 분석 vs 코딩)로 효과 차이가 있는지 실험해보고 싶다.
- "덜 중요한 제약은 다음 턴에 요청해도 늦지 않다"는 원칙과, 초기 프롬프트에 최소한의 구조를 남겨야 재작성 비용이 줄다는 실무 경험 사이의 균형점은 어디인가.
- Interviews 기법을 실무 문서 작성에 쓸 때 AI가 질문을 너무 많이/사소하게 던지는 경우의 조절 방법 (질문 개수·깊이 제한 프롬프트).
