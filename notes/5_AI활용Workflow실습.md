# Chapter 5. AI 활용 Workflow 실습 — 핵심 요약 노트

> 원문: `markdown/5_AI 활용 Workflow 실습_r3.md` (총 46페이지)

## 챕터 개요

이 챕터는 "불량 검증에 AI를 도입하여 업무 효율화"라는 가상 시나리오의 제안서를 처음부터 끝까지 AI와 함께 만들어보는 실습이다. 반도체 클린 장비·웨이퍼 이송(카트)·초정밀 카메라 촬영·AI 불량 판별이라는 배경 설정 위에서, **목적 수립 → 데이터 조사 → 데이터 선별 → 슬라이드 제안서 작성 → 인터랙티브 웹 제안서 작성**의 5단계 범용 Workflow를 단계별로 진행한다. 각 단계에서 사용할 프롬프트가 구체적으로 제시되는 것이 특징이며, 사람이 중간에 개입해 점검하는 Human-in-the-Loop 개념을 실천한다. 최종 산출물은 프로젝트 목적 docx, 리서치 결과물(docx + html), 슬라이드 제안서(pdf), 인터랙티브 웹 제안서(html)이다.

## 핵심 요점

### 0. 실습 배경 시나리오 (Unit 1)

- 주인공은 공정 AI 팀에 배치된 AI 엔지니어. 클린 장비에서 세정을 마친 웨이퍼는 이송 장비(카트/OHT)에 실려 이동한다.
- 카트에 초정밀 카메라를 설치하면 고해상도·적외선 등 다양한 이미지를 얻을 수 있고, 이미지만 확보되면 AI로 불량 여부 판별이 가능하다(본인은 이 부분 전문성 보유).
- 불량 판정 시 카트가 웨이퍼를 세정 장비로 재이송하거나, 불량이 심하면 폐기 신호를 보내는 자동화가 가능하다.
- 문제: 반도체 공정 도메인 지식이 부족해 제안서 작성 방법을 모른다는 것 → 이를 AI Workflow로 해결하는 것이 실습의 출발점.

### 1단계. 목적 수립 — 배경·목적 설정 (Unit 1)

- **새 대화 + 상황 설명**: 상황을 1분간 읽고 이해한 후 프롬프트에 넣는다. 핵심 프롬프트는 "내가 지금 어떤 상황인지 설명해 볼게. 우선 상황만 이해해 줘. (내가 요청하기 전까지는 제안서를 작성하지 말아 줘.)" — AI가 선제적으로 결과물을 만들지 못하게 제어하는 것이 포인트다.
- **Blindspot pass**: "도메인 지식이 전혀 없는 상황인데 내가 알아야 할 내용이 뭐가 있을까? 핵심 키워드와 과정을 중학생도 쉽게 이해할 수 있는 설명을 Web App(Canvas)으로 생성해서 보여줘" — 내가 놓친 정보·관점을 AI로 탐색한다.
- **Interview**: Canvas를 끄고 "혹시 내가 어떤 상황인지에 대해 덜 설명한 게 있는지 모르겠네. 한번 나를 인터뷰해 줘 (한번에 하나의 질문 씩, 중요한 거 2개만 답변할 거야)" — 부족한 정보를 AI와 문답으로 보강한다.
- **목적·배경 정리 + Docs 저장**: "목적/배경을 정리해서 글로 정리해 봐" → Docs로 내보내기 → docx 다운로드. 이 파일이 이후 자료 수집 시의 '목적 파일'이 된다.
- **트러블슈팅**: 내보내기가 안 되면 로딩 메시지 닫기 → Ctrl+Shift+R(강력 새로고침) → 'Docx로 내보내기' 재시도. 그래도 안 되면 크롬 재시작, 또는 학습자료의 완성본 zip 파일로 실습 진행.

### 2단계. 데이터 조사 — 딥리서치 병렬 수행 (Unit 2)

- 조사 담당 팀원 2명을 고용했다고 가정하고, **두 개의 새 채팅에서 딥리서치를 병렬**로 돌린다.
- **조사 1 (카메라 종류)**: 목적 파일을 드래그로 업로드 후 딥리서치 클릭, 프롬프트 "사용할 수 있는 초정밀 카메라 종류에 대해 조사를 해줘". 연구 계획이 세워지면 '연구 시작' 버튼 클릭.
- **조사 2 (유사 사례)**: 새 채팅에서 딥리서치, 프롬프트 "목적과 유사한 사례가 있는지 실제 사례 및 제품 등 조사해 줘".
- **Docs 저장**: 조사 결과 2개를 각각 Docs 내보내기 → docx 다운로드 (단, "Docs 내보내기"는 한 번만 클릭).
- **[이미지 확인] p22 흐름도**: "공유 및 내보내기 > Docs로 내보내기" 클릭 → 워드 아이콘 파일이 열림 → "1분간 로딩 기다리기(화면 정지됨)" 안내 → 완성된 docx 파일 2개(예: 세정 공정 AI 검사 사례.docx, 초정밀 카메라 종류 조사.docx)가 생성됨. 만들어지는 파일명은 조사 결과에 따라 달라질 수 있다는 안내가 함께 표시됨.
- **시각화**: "AI 시대에는 글보다 시각적으로 정리된 글이 이해가 빠르다" → 딥리서치 결과 > 공유 및 내보내기 > **웹페이지 생성**으로 html 시각화본 추가. 최종적으로 글 기반 docx 2개 + 시각화 html 2개, 총 4개 파일 완성.
- **[이미지 확인] p23 흐름도**: "공유 및 내보내기 > 웹페이지" 클릭 → 코드/미리보기 화면에서 다운로드 버튼(빨간 박스로 강조) 클릭 → Chrome 아이콘의 html 파일 2개(예: code_artifact(4).html, in_line_ai_inspection_spa.html) 완성.
- **미션 6-1 제출**: 프로젝트 목적 docx + 카메라 리서치 결과물(html) 제출.

### 3단계. 데이터 선별 — Human-in-the-Loop 의견 반영 (Unit 3)

- 조사한 데이터를 전부 쓰지 않고, 파악 후 제안서에 넣을 내용만 골라야 한다.
- 새 채팅에서 목적 파일 + 딥리서치 결과 파일 2개 업로드. 프롬프트: "프로젝트 목적과 관련된 조사 자료 2개를 줄게. 최종 제안서에 사용할 데이터를 선별하고자 해. 먼저 내용을 모두 이해만 해 줘. 쓸만하거나 불필요한 부분에 대해 내가 직접 의견을 줄 거야."
- 웹 기반 html 문서를 보며 사람의 의견을 전달한다 — 예: "Latency 데이터는 모두 빼자, 동일한 조건으로 측정이 아닌 것 같아", "적외선 카메라랑 비전 카메라 2개 말고는 불필요할 것 같아", "상용 솔루션 사례는 모두 마음에 안 들어, 모두 빼자."

### 4단계. 슬라이드 제안서 작성 — 계획 먼저, 생성 나중 (Unit 4)

- **Human-in-the-Loop 개념**: 실제 문서 제작 전 인간이 중간 점검을 해야 더 좋은 결과물이 나온다. 최종 완성 후의 수정 요청은 의도대로 반영이 잘 안 되므로, 완성 후 수정보다 **중간 단계에서 방향을 점검**하는 것이 효과적이다.
- **PLAN 문서 작성 지시**: 새 대화가 아닌 기존 대화(선별한 세션)에 이어서, Canvas 추가 후 프롬프트: "프레젠테이션 형태의 제안서를 만들기 전에 먼저 계획을 세워 줘. 계획을 내가 검토해 볼 거야. 각 Page 별로 어떤 내용을 구성할지 제안서 작성을 위한 계획문서 작성해 줘" — 슬라이드를 즉시 만들라는 지시가 아니라 계획을 검토하겠다는 뜻.
- **계획 문서 검토**: Docs에서 충분히 검토(Human-in-the-Loop) → 결과물 예상 → docx 다운로드.
- **슬라이드 생성**: 새 대화 + Canvas에서 분석 슬라이드 생성 지시. 컬러 디자인 시스템을 못 정했으므로 "밝은 것부터 어두운 배경을 포함해서 디자인 시스템 후보 16개를 보여주는 인터랙티브한 Web App을 만들어 줘" → 후보 1~16 중 하나를 선택해 답변(예: "후보 2번으로 슬라이드 제안서 만들어 줘").
- **완성본 다운로드**: 완성된 슬라이드를 PDF로 다운로드(최대 2분 소요).

### 5단계. 인터랙티브 웹 기반 제안서 작성 (Unit 5)

- **계획 문서 생성**: "나는 인터랙티브한 요소들이 많이 들어있는 Web 기반 제안서를 만들어야 해. 전달한 슬라이드를 쉽게 이해할 수 있는 인터랙티브한 웹 앱 제안서가 필요해. 아이디어를 제안하는 것이고 도메인 지식이 없는 엔지니어도 이해 가능해야 해. 특히 Vision 카메라와 적외선 카메라 동작 예시를 인터랙티브하게 만들어 줘야 해. 내가 직접 최종 제안서를 만들라고 지시할 때까지 만들지 말아 줘. 위 내용을 포함하여 어떤 내용을 구성할지 제안서 작성을 위한 계획문서 작성해 줘."
- **계획 문서를 Gemini와 함께 수정**: "너가 작성해 준 제안서 수정하자. 내가 전달한 슬라이드(pdf)를 더 쉽게 이해할 수 있는 제안서가 목적이야. 무엇인지 매우 가볍게 설명하고, 바로 시뮬레이터로 예시와 함께 먼저 이해할 수 있도록 하자. 순서를 바꿔 줘." — 계획 단계에서도 사람이 개입해 다듬는다.
- **디자인 시안 선택**: "단순한 느낌부터 화려한 갤러리 느낌까지 디자인 시안 후보 4개를 보여주는 인터랙티브한 Web App을 만들어 줘" → 후보 1~4 중 선택 후 답변(예: "후보 2번으로 Web App 만들어 줘").
- **미션 6-2 제출(필수 과제)**: 슬라이드 제안서 pdf + 인터랙티브 웹 제안서 html 제출.
- **[이미지 확인] p44 제출 화면**: AI Studio 좌측 메뉴(대시보드/공지사항/AI 갤러리/학습자료/과제/평가/설문) 중 "과제" 클릭 → 제출 목록에 ① 슬라이드 제안서.pdf(빨간 PDF 아이콘), ② 인터렉티브 제안서.html(Chrome 아이콘) 2개 파일을 업로드하는 화면.

### 정리 — 활용한 Workflow

목적 수립(배경·목적 docx) → 2개 Agent가 딥리서치로 자료 조사 → Human-in-the-Loop로 데이터 선별 → 계획문서 작성·검토 후 슬라이드(pdf)와 Web 기반 제안서(html) 제작. 하나의 작품을 만들기 위해 Workflow에 맞게 AI에 지시하는 과정 전체를 리뷰.

## 실습/적용 포인트

- **"만들지 말고 이해만 해 줘" 패턴**: 상황 설명·자료 파악 단계마다 "요청하기 전까지 작성하지 말아 줘" / "이해만 해 줘"로 AI의 선제 출력을 차단하는 프롬프트 제어 기법을 반복 연습할 수 있다.
- **병렬 딥리서치**: 한 채팅에서 순차적으로 묻는 대신, 주제별 새 채팅 + 딥리서치로 동시에 조사시켜 시간을 절약하는 멀티 에이전트 활용법.
- **선별은 사람이**: AI가 조사한 데이터의 취사선택(Latency 제외, 카메라 2종만 유지, 상용 사례 제외 등)은 사람의 판단으로 진행 — 데이터 품질이 최종 제안서 품질을 좌우한다.
- **계획 문서 먼저(Human-in-the-Loop)**: 완성물 수정 요청은 잘 반영되지 않으므로, PLAN 문서(페이지별 구성안)를 먼저 받아 검토한 뒤 생성 지시하는 습관이 핵심이다.
- **선택지를 Web App으로 받기**: 디자인 시스템 후보 16개, 디자인 시안 후보 4개처럼 선택이 필요한 사항은 인터랙티브 Web App(Canvas)으로 후보를 보여달라고 하고 번호로 고르는 방식이 효율적이다.
- **시각화 내보내기**: 딥리서치 결과는 docx(글 기반)와 html(웹페이지 생성, 시각화 기반) 두 형태로 모두 남기면 검토·공유가 쉽다.
- 실습 산출물 예시는 `source/workflow_samples/`에서 확인 가능: 1_프로젝트_목적.docx, 2_리서치결과(세정 AI 사례 / 초정밀 카메라 조사).docx, 3_리서치보고서(html 2종), 4_슬라이드_제안서_계획문서.docx, 5_슬라이드_최종제안서.pdf, 5_인터렉티브_최종제안서_.html.

## 궁금한 점

- 슬라이드 제안서 생성을 "새 대화"에서, 계획 문서는 "기존 대화"에서 지시하는 이유(컨텍스트 유지 vs 초록 상태 활용)의 기준이 명확히 설명되지 않았다 — 아마 결과물 생성 시엔 선별된 맥락만, 계획 수립 시엔 전체 맥락이 필요해서로 추정.
- 딥리서치 결과의 웹페이지(html) 생성이 조사 2건 모두에서 필수인지, 카메라 리서치 1건만 제출하면 되는지(미션 6-1은 카메라 리서치 결과물 html 1개만 요구)의 대칭이 살짝 안 맞는다.
- 데이터 선별 단계에서 사람 의견을 반영한 후, 선별 결과를 별도 파일로 저장하는 절차가 원문에 명시되지 않았다 — 다음 단계(슬라이드 계획)에서 "기존 대화에 이어서" 진행하므로 세션 맥락에 의존하는 것으로 보인다.
